# 3D and WebGL

3D is worth using when it shows something flat layout can't: depth, a space to move through, an object to inspect, or a material with light and texture. If a flat image, SVG, or simple CSS would do the same job, use that.

## Decide whether 3D earns its place

- Name what the 3D shows that the page needs.
- Name what happens without it. If the answer is "nothing important," it's decoration. Cut it or make it lighter.
- Name the flat alternative for the same beat: a still image, an SVG, or a CSS version. If the flat version works, consider using it.
- Name the moment it appears in the story. 3D should be placed where it supports a beat, not spread across the whole site.

## Building the scene

- Start with the smallest scene that can carry the idea. Add complexity only when the idea needs it.
- Keep one shared visual language across the scene and the page: the same colors, the same lighting direction, the same motifs.
- Use real units and a consistent scale. Objects that look right at one size but wrong at another break the illusion.
- Set the budget before modeling: triangles per scene, texture size, draw calls, and total download in KB. Write the numbers in `DESIGN.md`. Target 60fps on a mid-range phone.
- Fake what you can. Use matcaps instead of real reflections, baked lighting instead of live lights, billboarded sprites for glow, a blurred layer instead of real depth of field, and simulations (fluid, particles) at a fraction of screen resolution.

## Compression

- Use glTF or GLB for models.
- Compress geometry with Draco or Meshopt when the file size warrants it.
- Use KTX2 for compressed textures.
- Check the total download on a throttled connection, not only the file size on disk.

## Renderer

- three.js removed WebGL1 in r163. `WebGLRenderer` is WebGL2-only, so don't plan a WebGL1 fallback.
- Check support before starting the scene:

```js
import WebGL from "three/addons/capabilities/WebGL.js";
if (!WebGL.isWebGL2Available()) showStaticFallback();
```

- `WebGPURenderer` from `three/webgpu` falls back to a WebGL2 backend when WebGPU is missing. Call `await renderer.init()` before the first render.
- Cap pixel ratio. Most scenes should use 1.5 to 2 at most:

```js
renderer.setPixelRatio(Math.min(window.devicePixelRatio, 2));
```

- Use one renderer per page. Keep one canvas alive across sections and routes. When content changes, swap the scene's contents, not the renderer.
- To place DOM content on 3D planes, keep the DOM element as the source of truth and sync its position and size to the plane each frame. See `recipes/dom-gl-sync.js`.
- React Three Fiber v9 is the current stable release (v10 is in alpha). Use it only when the project is already React. Don't add React to a plain site just for a 3D scene.

## Rendering budget

- Cap pixel density at 1.5 to 2 for most scenes. Full device pixel ratio on high-DPI phones can be expensive without visible gain.
- Use adaptive quality. Watch frame time, and lower resolution or effects when frames run long. Raise them again when there's headroom.
- Render only when something changes, or keep rendering at a steady rate and avoid recreating objects every frame.
- Dispose geometries, materials, and textures when a scene is removed. Leaking memory is one of the most common causes of slow 3D pages.
- Pause rendering when the canvas is off-screen or the tab is hidden.

## Input

- Pointer input should work on touch too. Map mouse movement and touch drag to the same behavior.
- Design the touch equivalent when you design the cursor idea, not after. A cursor-follow light becomes a drag or a scroll-driven move on touch. See `recipes/pointer-effects.js`.
- Use a raycaster for hover and click on objects. Keep the hit targets large enough to use on a phone.
- Provide a keyboard path to every interaction that matters: focusable controls that move the camera or trigger the same actions.
- Don't rely on hover alone. A visitor on a phone must be able to reach the same content.

## Feature detection and fallback

- Check WebGL2 support before starting (see the Renderer section). If it's missing, show the non-3D version.
- The fallback is part of the design. Plan it when you plan the scene.
- A non-WebGL visitor still needs the same content: the same story beats, in the same order, with the same text and links. Use images, a short video, or simpler motion. A looping video must pause under reduced motion.
- Show a clear message if 3D isn't available. A blank canvas with no explanation is a failure.

## Text in 3D

- Keep text as DOM. Do not render headlines or body copy only as SDF or MSDF text in WebGL. See `references/typography.md`.
- Overlay text on the canvas must keep enough contrast against whatever is behind it.

## Loading

- Load the first visible scene first. Defer everything else until it's needed.
- Load the renderer and the first model only when the scene is near the viewport.
- Show progress during long loads. See `references/loaders.md`.
- Don't block the whole page on the 3D scene. Let the text and layout appear first when possible.

## Accessibility and motion

- Reduced motion applies to 3D too. Stop camera drift, orbit, particles, and looping motion, or replace them with a still frame.
- Make sure text overlays on 3D have enough contrast against whatever is behind them.
- Don't use flashing lights or rapid strobing effects. No more than three flashes per second (WCAG 2.3.1).

## Checks

- Does the scene have a clear reason to exist in the story?
- If the beat works flat, is the scene still worth its cost?
- Does it run at an acceptable frame rate on a mid-range phone, with the budget written down?
- Does the page still make sense with WebGL off?
- Are all the visitor's options available without a pointer?
- Is the canvas paused when it is off-screen or the tab is hidden?
- Are models, textures, and scripts loaded only when needed, and released when not?
